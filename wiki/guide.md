# 처음 사용하는 분을 위한 Keepiluv LLM Wiki 안내서

이 안내서는 개발, Git, Markdown, Obsidian, LLM을 몰라도 Wiki를 사용할 수 있도록 설명합니다. 대부분의 작업은 명령어 대신 Codex에게 평소 말하듯 요청하면 됩니다.

## 한 문장으로 설명하면

**Keepiluv LLM Wiki는 프로젝트의 지식 베이스를 한곳에 보관하고, AI가 스스로 변화를 찾아 진화하는 지식 관리 시스템입니다.**

생활 속 도서관에 비유하면 다음과 같습니다.

- `wiki/index.md`는 안내 데스크입니다.
- 공식 문서는 직원이 확인한 기준 자료입니다.
- 쉬운 해설 문서는 여러 기준 자료를 연결한 안내 책자입니다.
- Codex는 새 자료와 오래된 자료를 찾아 승인된 작업 범위에서 정리하는 사서입니다.
- 사용자는 본작업 밖의 새로운 의미와 Git 공유를 결정하는 책임자입니다.

Codex가 정리를 돕지만, 중요한 뜻을 마음대로 바꾸지는 않습니다.

## 공식 문서와 쉬운 해설

문서에는 두 가지 역할이 있습니다. 영어 표시는 문서를 관리하기 위한 이름일 뿐이므로 먼저 쉬운 뜻을 기억하면 됩니다.

| 쉬운 이름 | 관리 표시 | 의미 |
|---|---|---|
| 공식 기준 문서 | `canonical` | 프로젝트 사실과 운영 정책을 정하는 기준입니다. |
| 연결 해설 문서 | `synthesized` | 여러 공식 문서를 연결해 쉽게 설명한 문서입니다. |

`wiki/reference`, `wiki/operations`, `wiki/schema`의 문서는 공식 기준입니다. `wiki/topics`는 AI가 공식 기준을 연결해 설명하는 공간입니다. 두 내용이 다르면 공식 기준 문서를 우선하고, 필요하면 실제 코드와 Agent 작업 규칙까지 다시 확인합니다.

예전에 별도 문서 폴더에 있던 지식은 현재 Wiki로 통합되었습니다. 지금은 `wiki/`가 프로젝트의 **유일한 공식 지식 베이스**입니다.

`wiki/index.md`가 모든 지식 탐색의 시작 화면입니다. 찾고 싶은 것이 있으면 직접 폴더를 뒤지기보다 Index에서 링크를 따라가거나 Codex에게 찾아 달라고 요청하세요.

Obsidian이 없어도 GitHub나 일반 문서 편집기에서 읽을 수 있습니다. Obsidian은 문서와 연결 관계를 편하게 보여주는 화면입니다.

## 화면과 폴더의 역할

| 위치 | 하는 일 | 주로 보는 사람 |
|---|---|---|
| `wiki/index.md` | 모든 중요 문서로 이동하는 시작 화면 | 모든 사용자 |
| `wiki/reference` | 프로젝트 개요, 구조, 용어, 테스트 같은 공식 지식 | 운영자, 기획자, 개발자, AI |
| `wiki/operations` | 어떤 Agent가 어떤 순서로 일하는지 정한 공식 운영 지식 | 운영 담당자, AI |
| `wiki/schema` | Wiki를 추가·검사·갱신하는 공식 관리 규칙 | Wiki 관리자, AI |
| `wiki/topics` | 여러 공식 문서를 연결해 쉽게 설명한 해설 | 모든 사용자 |
| `wiki/inbox` | 미정리 새 자료와 작업 중 발견한 비공식 지식 후보를 두는 곳 | 자료를 추가하는 사람, AI |
| `wiki/sources` | 외부 자료의 주소와 확인 정보를 기록하는 곳 | Wiki 관리자, AI |
| `wiki/decisions` | 중요한 결정과 그 이유를 기록하는 곳 | 의사결정자 |
| `wiki/attachments` | 공개 가능한 이미지와 첨부파일을 두는 곳 | 모든 사용자 |
| `wiki/templates` | 새 문서를 일정한 형식으로 만드는 양식 | Wiki 관리자, AI |
| `wiki/log.md` | Wiki에서 어떤 작업을 했는지 남긴 기록 | 운영 담당자 |

## 문서 출처

`sources`는 **Wiki 외부 자료를 다시 확인해야 할 때만 남기는 외부 근거 목록**입니다.

쉽게 구분하면 다음과 같습니다.

| 표시 | 쉬운 의미 | 사용하는 경우 |
|---|---|---|
| `sources` | 외부 자료를 다시 찾기 위한 영수증 | 외부 공식 문서, 웹페이지, 다른 저장소의 코드가 결론의 근거인 경우 |
| 일반 문서 링크 | Wiki 안의 관련 문서로 가는 길 | 다른 Wiki 문서를 참고하거나 함께 읽어야 하는 경우 |
| `source_paths` | 연결 해설이 참고한 공식 Wiki 목록 | `synthesized` 문서가 여러 공식 문서를 묶어 설명하는 경우 |

### `sources`를 기록하는 예

- 외부 서비스의 공식 정책을 확인하고 Wiki에 적용 기준을 정리한 경우
- 다른 저장소의 특정 코드가 장기적으로 확인해야 할 기술 근거인 경우
- 외부 표준 문서나 공식 안내 페이지를 요약한 경우

이때는 자료의 주소와 확인 날짜를 남깁니다. GitHub 코드는 나중에 내용이 바뀌지 않도록 특정 커밋에 고정된 주소를 사용합니다.

### `sources`를 기록하지 않는 예

- 프로젝트 내부에서 새로 합의한 공식 정책
- 기존 Wiki 문서를 정리하거나 표현만 쉽게 바꾼 경우
- 과거 문서 폴더에서 Wiki로 옮겼다는 이동 이력
- 작업에 사용한 Pull Request 번호
- 같은 Wiki 안에 있는 다른 문서

Wiki 내부 문서는 일반 링크로 연결하고, 여러 공식 문서를 종합한 해설은 `source_paths`로 연결합니다. 따라서 대부분의 공식 Wiki 문서에는 `sources`가 없어도 정상입니다.

외부 근거를 기록해야 할지 확실하지 않다면 직접 형식을 작성하기보다 다음처럼 요청하세요.

> 이 문서에 외부 출처 기록이 필요한지 판단해줘.

자세한 형식은 [출처 정책](schema/source-policy.md)에서 확인할 수 있습니다.

## 평상시 사용하는 네 가지 방법

### 1. 공식 정책 찾아보기

궁금한 내용을 Codex에게 자연어로 질문합니다.

> 휴가 기능을 만들 때 따라야 할 공식 원칙을 Wiki에서 찾아 쉽게 설명해줘.

Codex는 `wiki/index.md`에서 시작해 관련 공식 문서를 찾고, 필요하면 쉬운 해설과 실제 작업 규칙을 함께 확인합니다. 질문만 하는 동안 문서는 바뀌지 않습니다. 답변에는 어떤 문서를 근거로 사용했는지 함께 보여 달라고 요청할 수 있습니다.

### 2. 새 자료 추가하기

회의 메모와 참고 링크는 `type: source`, 작업 중 발견한 재사용 지식은 `type: knowledge-candidate`로 `wiki/inbox`에 둡니다. 둘 다 아직 공식 지식은 아닙니다.

> `wiki/inbox`의 회의 메모를 읽고 기존 공식 지식과 어떤 관계인지 확인해줘. 아직 문서는 바꾸지 말고 정리안만 보여줘.

Codex는 공개 가능 여부, 출처, 기존 문서와의 중복이나 충돌을 확인하고 변경안을 제시합니다. 이런 독립적인 자료 추가는 내용을 검토한 뒤 **Wiki에 반영해도 된다고 승인해야** 실제 문서가 바뀝니다. 이미 승인한 구현 작업에서 확인된 장기 지식은 별도 Wiki 승인 없이 함께 갱신됩니다.

외부 글은 전체를 복사하기보다 주소, 확인 날짜, 핵심 요약을 남깁니다.

지식 후보는 검색하거나 읽은 횟수가 아니라, 서로 다른 작업에서 계획·구현·테스트·리뷰 판단에 실제 사용한 횟수와 근거를 남깁니다. 일반 후보는 독립 작업 2회 이상 사용되면 공식 문서 승격을 검토하고, 제품 정책·사용자 흐름·데이터 안전 규칙은 횟수와 관계없이 바로 검토할 수 있습니다. 어느 경우도 자동 승격하지 않으며 Draft PR에서 사용자가 확인합니다.

### 3. Wiki 변경 상태 확인하고 갱신하기

공식 지식이나 Agent 규칙이 바뀌었을 가능성이 있으면 다음처럼 요청합니다.

> Wiki 변경 상태를 확인하고, 영향을 받는 문서를 쉬운 말로 알려줘. 수정은 하지 마.

AI는 새로 생긴 문서, 바뀐 문서, 사라진 문서와 영향을 받을 수 있는 해설 문서를 찾아냅니다. 이후 다음 순서로 진행합니다.

1. Codex가 변경 내용과 승인된 본작업 범위를 비교합니다.
2. 본작업에서 생긴 장기 지식, Wiki와 코드의 불일치, 재사용 운영 규칙을 자동으로 갱신합니다.
3. 본작업과 무관한 새 의미 결정이 필요하면 사람에게 승인을 요청합니다.
4. `Keepiluv-Agent` 저장소 루트에서 문서, Index, 작업 기록을 갱신하고 검사합니다.
5. 관련 테스트와 validator를 실행합니다.
6. 다른 미승인 변경이 승인 범위에 섞이지 않았는지 확인합니다.
7. 안전한 경우에만 승인된 본작업 범위를 **Wiki 검증 기준점**(다음 비교의 기준 상태)으로 확정합니다.
8. Wiki 관련 파일만 바뀐 작업은 변경 기록을 자동으로 커밋하고 GitHub에 Draft PR로 올립니다. 제품 기능 코드가 섞이면 커밋과 공유를 사람이 별도로 승인합니다.

**Wiki 검증 기준점 확정**은 “여기까지 확인했으니 다음 검사부터는 이 상태와 비교하자”는 뜻입니다. 일반 코드에서는 **커밋과 공유**를 별도로 승인합니다. 다만 승인된 Wiki 전용 작업은 검사가 끝나면 AI가 커밋과 Draft PR 생성까지 이어서 처리합니다.

### Draft PR에서 검토하는 방법

Draft PR은 아직 최종 병합 준비가 끝났다고 선언하지 않은 검토 공간입니다.

1. AI가 관련 Wiki 변경을 한 작업 단위로 묶어 Draft PR을 만듭니다.
2. 사용자는 GitHub에서 바뀐 문장을 읽고 원하는 부분에 리뷰 코멘트를 남깁니다.
3. AI는 코멘트를 확인해 승인된 범위 안에서 문서를 수정하고 답변합니다.
4. AI는 검사를 다시 실행하고 같은 Draft PR에 변경을 올립니다.
5. 최종 내용이 맞는지 승인하고 병합하는 일은 사용자가 수행합니다.

AI는 Draft PR을 자동으로 병합하지 않습니다. 제품 기능 코드가 함께 바뀌었거나 새 정책 판단이 필요하면 자동 흐름을 멈추고 기존 승인 절차로 돌아갑니다.

### 4. 잘못되거나 충돌하는 내용 바로잡기

내용이 이상하다고 바로 삭제하지 말고 근거를 먼저 비교합니다.

> 이 문장이 공식 정책과 맞는지 확인하고, 충돌한다면 양쪽 근거와 수정안을 보여줘. 승인 전에는 바꾸지 마.

Codex는 공식 기준, 연결 해설, 실제 작업 규칙을 비교합니다. 어느 쪽이 맞는지 확실하지 않으면 `확인 필요`로 남기고 사람에게 판단을 요청합니다. 오래된 내용은 흔적 없이 지우기보다 더 최신인 문서와 연결해 보존할 수 있습니다.

## 자동 유지보수의 범위

여기서 “자동”은 승인된 본작업 범위 안의 지식 동기화를 다시 묻지 않고 수행한다는 뜻입니다. 본작업 밖의 새로운 의미와 공유 여부는 사람이 결정합니다.

| 구분 | AI가 자동으로 돕는 일 | 사람이 승인하거나 판단하는 일 |
|---|---|---|
| 상태 확인 | 새 문서, 변경 문서, 삭제 문서 탐지 | 어떤 변화가 올바른지 판단 |
| 영향 분석 | 함께 확인해야 할 해설 문서와 승인 범위 찾기 | 본작업 밖의 새 의미 결정 |
| 문서 갱신 | 승인된 본작업의 장기 지식과 Wiki 불일치 반영 | 본작업 밖의 정책 변경 승인 |
| 품질 검사 | 깨진 링크, 누락된 정보, 의심되는 비밀정보 찾기 | 범위 밖 수정안 적용 여부 결정 |
| 기준 관리 | validator 통과 후 승인 범위를 다음 비교 기준으로 기록 | 다른 미승인 변경이 섞였을 때 처리 결정 |
| 변경 공유 | 일반 코드의 커밋 후보 준비, Wiki 전용 작업의 자동 커밋과 Draft PR·리뷰 반영 | 일반 코드의 커밋·공유 승인, Draft PR 최종 승인과 병합 |

상태 확인과 질문은 기본적으로 읽기 전용입니다. 승인된 본작업 안의 동기화는 자동으로 적용하고, 그 밖의 의미 변경은 반드시 사람의 승인을 받습니다.

## Codex에게 요청하는 문장

아래 문장을 그대로 사용하거나 상황에 맞게 바꿀 수 있습니다.

### 찾아보기

1. `wiki/index.md를 기준으로 이 Wiki에 어떤 공식 지식이 있는지 쉽게 설명해줘.`
2. `이 기능과 관련된 공식 정책을 찾아서 출처와 함께 알려줘.`
3. `공식 기준 문서와 쉬운 해설 문서의 차이를 보여줘.`
4. `이 질문에 Wiki를 근거로 답하고, 근거가 부족하면 확인 필요라고 표시해줘.`

### 새 자료와 갱신안

5. `wiki/inbox의 새 자료를 검토하고 어디에 정리할지 제안해줘. 아직 수정하지 마.`
6. `이 웹페이지를 공개 Wiki에 추가해도 되는지 먼저 확인해줘.`
7. `이 자료와 기존 공식 지식의 중복이나 충돌을 찾아줘.`
8. `이 자료를 반영할 변경안을 보여주고 사람이 확인할 부분을 표시해줘.`

### 상태 확인과 갱신 승인

9. `Wiki 변경 상태를 확인하고 영향받는 문서를 쉬운 말로 알려줘. 수정하지 마.`
10. `상태 보고서에서 의미가 달라지는 부분만 따로 설명해줘.`
11. `방금 보여준 Wiki 갱신안을 승인해. 승인한 범위만 반영하고 검사 결과를 알려줘.`
12. `승인된 본작업 범위만 자동 동기화하고, 다른 변경이 섞이면 기준 상태를 확정하지 마.`
13. `검사가 모두 통과했고 다른 미승인 변경이 없다면 승인 범위를 새 비교 기준으로 확정해줘.`

### 검사와 커밋 준비

14. `Wiki 전체를 검사하고 수정하지 말고 문제 목록만 보여줘.`
15. `깨진 링크, 출처 누락, 공식 문서와의 충돌을 확인해줘.`
16. `공개 저장소에 올리면 안 되는 정보가 있는지 검사해줘.`
17. `승인한 변경만 커밋할 준비를 하고, 파일과 변경 내용을 먼저 설명해줘.`
18. `기준 상태 확정과 커밋이 각각 무엇을 바꾸는지 설명하고, 커밋은 별도로 승인받아.`

## 보안과 공개 저장소 주의

이 Wiki는 공개 GitHub 저장소에 공유될 수 있습니다. 한 번 공개된 정보는 나중에 삭제해도 복사본이나 변경 기록에 남을 수 있습니다.

다음 내용은 `wiki/inbox`, `wiki/sources`, `wiki/topics`, `wiki/attachments`를 포함해 어디에도 넣지 마세요.

- 비밀번호와 로그인 정보
- 인증 토큰, 개인키, 서명 파일
- 서비스 접속용 비밀값
- 주민등록번호, 전화번호, 집 주소 등 개인정보
- 공개되지 않은 고객 정보와 사내 기밀
- 원저작자의 허락 없이 복사한 외부 글 전체

공개 여부가 애매하면 저장하기 전에 Codex에게 민감정보 검사를 요청하고 사람이 다시 확인하세요. 자동 검사는 보조 장치이며 모든 위험을 찾아낸다고 보장할 수 없습니다.

## 자주 묻는 질문

### AI가 마음대로 Wiki를 수정하나요?

아니요. AI는 승인된 본작업에서 확인된 장기 지식과 Wiki 불일치를 반영하고, Wiki 관련 파일만 바뀐 경우 Draft PR까지 자동으로 준비합니다. 본작업과 무관한 의미 변경이나 새 정책 결정은 사람이 승인해야 하며, AI는 자동 병합하지 않습니다.

### 예전에 사용하던 원본 docs는 어디에 있나요?

기존 지식은 `wiki/reference`, `wiki/operations`, `wiki/schema`로 통합되었습니다. 현재 별도의 원본 docs 폴더는 사용하지 않으며, `wiki/`가 유일한 공식 지식 베이스입니다. 과거 위치가 필요한 경우에는 변경 이력과 출처 기록에서만 확인합니다.

### Obsidian이 꼭 필요한가요?

아니요. 문서는 일반 Markdown 파일이라 GitHub나 다른 편집기에서도 읽을 수 있습니다. Obsidian은 문서 목록, 검색, 링크 관계를 편하게 보여주는 도구입니다.

### 문서를 직접 수정해도 되나요?

가능합니다. 다만 승인된 본작업 밖에서 공식 기준을 바꾸는 수정은 Codex에게 영향 범위와 출처를 검사하게 하고, 팀의 승인 절차를 거쳐야 합니다. 잘 모르겠다면 직접 고치기보다 변경안을 요청하세요.

### `sources`가 없는 문서는 믿을 수 없는 문서인가요?

아니요. Wiki 자체가 프로젝트의 공식 지식 베이스이므로 내부 합의와 프로젝트 지식을 정리한 문서는 `sources`가 없어도 정상입니다. `sources`는 문서의 신뢰 등급이 아니라, 외부 자료를 다시 확인할 필요가 있을 때만 사용하는 선택 항목입니다.

### `sources`와 `source_paths`는 같은 것인가요?

아닙니다. `sources`는 Wiki 밖의 자료를 가리키고, `source_paths`는 쉬운 해설 문서가 참고한 Wiki 안의 공식 문서를 가리킵니다. 일반 사용자는 두 항목을 직접 관리하기보다 Codex에게 근거 관계를 확인해 달라고 요청하면 됩니다.

### Git을 몰라도 사용할 수 있나요?

네. 찾기, 질문, 초안 검토, 승인까지 자연어로 요청할 수 있습니다. 변경 이력을 남길 때도 Codex에게 파일과 내용을 쉬운 말로 설명해 달라고 한 뒤 커밋을 승인하면 됩니다.

### 변경 감지는 얼마나 자주 실행되나요?

현재는 정해진 시간마다 자동 실행되는 방식이 아닙니다. 사용자가 Codex에게 `Wiki 변경 상태를 확인해줘`라고 요청할 때 실행됩니다. 백그라운드 감시나 정기 실행은 현재 범위에 포함되지 않습니다.

### 여러 기기나 사람과 어떻게 동기화하나요?

팀 공유는 GitHub의 저장소 변경 이력을 통해 이루어집니다. 먼저 최신 내용을 받아오고, 승인된 변경을 커밋한 뒤 공유합니다. Obsidian Sync나 다른 파일 동기화 도구를 함께 쓰려면 충돌을 피하도록 팀에서 한 가지 방식을 정하세요. `.obsidian`의 개인 화면 설정은 기본 공유 대상이 아닙니다.

### 잘못 승인했을 때는 어떻게 하나요?

추가 변경을 멈추고 Codex에게 직전 변경 내용과 이전 상태의 차이를 보여 달라고 요청하세요. 아직 커밋하지 않았다면 승인한 범위만 되돌리는 수정안을 검토합니다. 이미 공유했다면 기록을 지우려 하지 말고, 잘못된 내용을 바로잡는 새 변경을 만들어 검토 후 커밋합니다. 비밀정보가 포함됐다면 일반 복구보다 먼저 저장소 관리자에게 노출 대응을 요청해야 합니다.

비밀정보가 노출된 경우에는 일반 문서 수정으로 끝내지 말고 즉시 저장소 관리자에게 알리세요. 이미 공개된 비밀값은 폐기하고 새 값으로 교체해야 합니다.

## 고급 참고

일반 사용자는 아래 명령을 직접 실행할 필요가 없습니다. Codex가 작업 결과를 설명하도록 요청하는 방식을 권장합니다.

```bash
./scripts/wiki-status.sh
./scripts/validate-wiki.sh
```

첫 번째 명령은 저장된 기준 상태와 현재 파일을 비교합니다. 이 비교 기준을 **Wiki 검증 기준점**(verification baseline)이라고 하며, `wiki/state/wiki-verification-baseline.tsv`에 파일 경로와 내용의 디지털 지문(SHA-256)을 저장합니다.

검사가 끝난 뒤 승인된 현재 상태를 새 기준으로 확정할 때만 다음 명령을 사용합니다.

```bash
./scripts/wiki-status.sh --accept --approved
```

이 명령은 본작업 승인을 기준 상태에 기록합니다. 일반 코드의 커밋·공유 승인이나 본작업 밖의 Wiki 의미 변경 승인을 대신하지 않지만, 승인된 Wiki 전용 작업에서는 이 검증 뒤 자동 커밋과 Draft PR 흐름이 이어집니다.
