# Test Strategy

이 문서는 Keepiluv의 테스트 전략에 대한 공통 source of truth입니다.
테스트 개수나 일률적인 커버리지 수치보다, 변경으로 발생할 수 있는 사용자 피해와 회귀 위험을 가장 경제적인 테스트 레벨로 줄이는 것을 목표로 합니다.

## 목표

- 핵심 도메인 규칙과 사용자 여정을 회귀로부터 보호한다.
- 실패 원인을 빠르게 찾을 수 있는 가장 낮은 테스트 레벨을 우선한다.
- 레이어 사이 계약과 실제 사용자 행동은 필요한 범위에서 더 넓은 테스트로 검증한다.
- 반복 실행해도 같은 결과가 나오는 안정적인 테스트를 유지한다.

## 현재 기준선

현재 저장소에서 확인되는 테스트 기반은 다음과 같습니다.

- JVM 단위 테스트: JUnit5, AssertJ, kotlinx-coroutines-test, Turbine, Kotlin Test
- Android/Compose 테스트 의존성 및 `AndroidJUnitRunner` 설정
- Domain 모델/UseCase 단위 테스트와 일부 ViewModel 테스트
- Fake Repository를 사용한 기존 테스트 패턴

Compose UI 테스트와 앱 전체 E2E 테스트는 전략상 필요한 레벨이지만, 현재 저장소에 실질적인 시나리오가 구축되어 있다고 간주하지 않습니다.
새 테스트를 계획할 때는 대상 모듈의 task, 실행 기기, 테스트 데이터와 서버 환경이 실제로 준비되어 있는지 먼저 확인합니다.

## 테스트 대상과 종류 선택

| 대상 | 기본 테스트 레벨 | 우선 검증 항목 |
|------|------------------|----------------|
| Domain 모델, UseCase, 유효성 규칙 | 단위 테스트 | 정상, 실패, 경계값, 상태 전이 |
| Repository 경계 | 통합 테스트 | 서버 요청 성공·실패와 결과 전달 |
| ViewModel, MVI Contract | 상태 통합 테스트 | Intent → State, Intent → SideEffect, 비동기 상태 흐름 |
| 핵심 Compose 화면 | UI 테스트 | 주요 사용자 행동, 로딩/오류/빈 상태, 입력 가능 여부 |
| 앱의 대표 사용자 여정 | 소수의 E2E 테스트 | 로그인/연결, 목표 수행, 인증샷 등 실패 비용이 큰 여정 |

이 표는 모든 기능에 모든 레벨의 테스트를 요구하지 않습니다. 같은 규칙을 여러 레벨에서 반복하기보다, 규칙은 낮은 레벨에서 자세히 검증하고 넓은 테스트에서는 연결과 대표 흐름만 확인합니다.

## 테스트 레벨 선택

다음 질문에 많이 해당할수록 테스트 우선순위와 테스트 범위를 높입니다.

1. 실패하면 핵심 기능을 사용할 수 없는가?
2. 조건, 시간, 상태 조합이 복잡한가?
3. 과거에 회귀가 발생했거나 변경이 잦은가?
4. 서버, DB, 파일, 시간, Android framework 같은 경계를 통과하는가?
5. 사용자가 직접 결과를 보거나 데이터가 변경되는가?

선택 원칙:

- 순수 로직과 도메인 규칙은 단위 테스트로 시작한다.
- Repository는 서버 또는 로컬 저장소 요청의 성공·실패가 앱에서 관찰 가능한 결과로 전달되는지 통합 테스트로 검증한다.
- 여러 실제 구현의 연결이 위험의 원인이면 통합 테스트를 선택한다.
- 화면 렌더링과 사용자 조작 자체가 요구사항이면 Compose UI 테스트를 선택한다.
- 여러 화면과 실제 앱 구성이 연결된 핵심 목적 달성만 E2E 테스트로 보호한다.
- 더 낮은 레벨로 동일한 위험을 충분히 검증할 수 있으면 더 넓은 테스트를 추가하지 않는다.

## 작업 유형별 완료 기준

### 버그 수정

- 가능하면 수정 전에 버그를 재현하는 실패 테스트를 작성한다.
- 재현 테스트가 구조적으로 불가능하거나 비용이 과도하면 이유와 수동 검증 절차를 남긴다.

### 신규 도메인 규칙

- 정상 동작, 실패 조건, 경계값을 검증한다.
- 시간 기반 규칙은 현재 시각을 직접 참조하지 않고 제어 가능한 시간 입력을 사용한다.

### ViewModel 변경

- 사용자 Intent에 따른 State 변화를 검증한다.
- 일회성 알림이나 이동은 SideEffect를 검증한다.
- 로딩, 성공, 실패 흐름 중 변경 위험과 관련된 상태를 포함한다.

### Repository 경계 변경

- DTO와 Domain 사이의 기계적인 변환 또는 단순 필드 매핑은 완료 조건에 포함하지 않는다.
- 서버 또는 로컬 저장소 요청의 성공·실패가 앱의 관찰 가능한 결과로 전달되는지 검증한다.

### 핵심 UI 변경

- 사용자가 수행하는 대표 행동과 관찰 가능한 화면 결과를 검증한다.
- 비즈니스 규칙 전체를 UI 테스트에서 다시 검증하지 않는다.
- UI 테스트 인프라가 없으면 이를 새로 도입할지, 낮은 레벨 테스트와 수동 검증으로 제한할지 계획에서 승인받는다.

### 핵심 사용자 여정 변경

- 장애 비용이 큰 대표 여정에 한해 E2E 시나리오를 검토한다.
- 실행 환경, 계정, 테스트 데이터, 서버 의존성을 통제할 수 있을 때만 자동화한다.
- 현재 E2E 기반이 없으면 존재하는 것처럼 완료 조건에 넣지 않고 도입 작업을 별도 범위로 분리한다.

## 테스트하지 않을 대상

- 단순 프로퍼티, 의미 없는 getter/setter
- Kotlin, Compose, Navigation 등 프레임워크 자체 동작
- 제품 요구사항이 아닌 픽셀 단위 배치와 구현 세부사항
- 관찰 가능한 결과와 연결되지 않은 private 함수 또는 호출 횟수
- 기계적인 DTO ↔ Domain 변환과 단순 필드 매핑
- 사용자 기능에 직접 영향을 주지 않는 nullable 매핑 방어
- 낮은 레벨에서 충분히 검증된 동일 규칙의 무분별한 중복
- 현재 인프라로 안정적으로 통제할 수 없는 네트워크/시간/외부 서비스 의존 시나리오

## Test Double 기준

- 실제 도메인 객체와 순수 로직을 우선 사용한다.
- Repository처럼 상태와 결과를 제어해야 하는 경계는 Fake를 기본으로 한다.
- Mock은 특정 함수의 호출 여부를 반드시 확인해야 하거나, Fake를 만들기 지나치게 어려운 경우에만 사용한다.
- 새 라이브러리가 필요하면 기존 의존성으로 해결 가능한지 먼저 확인하고, build 변경을 계획과 승인 범위에 포함한다.

## 실행 흐름

테스트 작업은 `Plan → Approve → Act → Review` 흐름을 따릅니다.

1. **Plan**: 위험, 테스트 레벨, 시나리오, 실행 명령, 제외 범위를 제안한다.
2. **Approve**: 계획이 필요한 작업은 사용자 승인으로 범위와 비용을 확정한다.
3. **Act**: tester가 성공 기준을 고정하고 implementer가 이를 만족하는 최소 구현을 수행한다.
4. **Review**: 관련 테스트와 정적 검증을 실행하고, 테스트 안정성·누락·과잉 결합을 검토한다.

작은 작업은 planner를 생략할 수 있지만, tester는 테스트 레벨과 제외 이유를 스스로 명시합니다.
tester의 반복 가능한 작성, 실행, 예외 처리, implementer handoff 절차는 `.agents/skills/test-workflow/SKILL.md`를 따릅니다.

## 안정성과 검증

- 테스트는 실행 순서, 실제 현재 시각, 공유 mutable state, 실서버 상태에 의존하지 않는다.
- 코루틴과 Flow는 테스트 dispatcher와 명시적인 대기/수집을 사용한다.
- 새 테스트는 가능하면 대상 테스트를 반복 실행해 비결정적 실패가 없는지 확인한다.
- 먼저 좁은 명령으로 빠르게 검증한 뒤 영향 범위에 맞는 모듈 task를 실행한다.

```bash
./gradlew :{module}:test --tests "{TestClass}"
./gradlew :{module}:test
```

Android/Compose UI 테스트는 대상 모듈과 기기가 준비된 경우에만 실행합니다.

```bash
./gradlew :{module}:connectedDebugAndroidTest
```

실제 Gradle task 이름이 다르면 `./gradlew :{module}:tasks --group verification`으로 확인합니다. 문서 변경은 `git diff --check`로 기본 형식을 검증합니다.

## 커버리지 원칙

- 커버리지는 목표가 아니라 미검증 영역을 찾는 탐색 지표로 사용한다.
- 전체 라인 커버리지 수치를 완료 조건으로 강제하지 않는다.
- 높은 커버리지보다 핵심 규칙, 실패 조건, 경계값, 사용자 여정의 시나리오 충족을 우선한다.
- 커버리지 도구나 기준을 도입하려면 별도 계획과 승인을 거친다.

## Agent 책임

| Agent | 책임 |
|------|------|
| `planner` | 리스크를 평가하고 적절한 테스트 레벨, 제외 범위, 실행 환경을 계획한다. |
| `tester` | 승인된 시나리오를 안정적인 테스트로 작성하고 실패 이유와 구현 조건을 전달한다. |
| `implementer` | 선행 테스트를 확인하고 승인된 범위의 최소 구현과 관련 검증을 수행한다. |
| `code-reviewer` | 테스트 레벨 적합성, 누락된 위험, 취약한 테스트와 과도한 구현 결합을 검토한다. |
